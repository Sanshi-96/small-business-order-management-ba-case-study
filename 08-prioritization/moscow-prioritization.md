# MoSCoW Prioritization

## 1. Purpose

The purpose of this document is to prioritize the identified user stories
based on their importance to the proposed order-management process.

MoSCoW prioritization is used to distinguish between requirements that are
essential, important, desirable, or outside the current scope.

The prioritization is based on the current understanding of the business
problem, identified requirements, stakeholder needs, and proposed To-Be
process.


## 2. MoSCoW Categories

The following categories are used:

| Category | Meaning |
|----------|---------|
| Must Have | Essential for the core business process or required outcome |
| Should Have | Important but the process may operate temporarily without it |
| Could Have | Desirable functionality that can be considered if resources allow |
| Won't Have | Not included in the current scope |

The prioritization should be validated with relevant stakeholders before
final implementation decisions are made.


## 3. Must Have

The following user stories are considered essential to the core
order-management process.

### US-01 — Place an Order

Customers must be able to place orders for the business to receive and
process customer requests.

### US-05 — View Centralized Orders

Order staff need a centralized view of orders to reduce the problems
associated with managing orders across multiple channels.

### US-06 — Review Order Information

Order staff need to review order information to identify missing or
incorrect information before processing.

### US-07 — Process an Order

Valid orders must be able to move through the operational fulfilment
process.

### US-08 — Update Order Status

Order status needs to be recorded so that the progress of orders can be
managed and monitored.

### US-09 — View Orders for Preparation

Packing staff need to identify orders that require preparation.

### US-11 — View Orders Ready for Delivery

Delivery staff need to identify orders that are ready for delivery.


## 4. Should Have

The following user stories are important but are not considered essential
to the minimum internal order-processing flow.

### US-02 — Receive Order Confirmation

Customers should receive confirmation after successfully submitting an
order to improve communication and confidence that the order was received.

### US-03 — View Order Status

Customers should be able to view the current status of their orders to
improve visibility and reduce unnecessary status enquiries.

### US-10 — Update Preparation Status

Packing staff should be able to record preparation progress so that other
authorized users can view the current order status.

### US-12 — Update Delivery Status

Delivery staff should be able to record delivery progress so that the
order lifecycle can be accurately tracked.


## 5. Could Have

No specific Could Have requirements have been identified at the current
stage of the case study.

Additional desirable features may be identified through further
stakeholder elicitation and can be considered if they provide business
value without affecting the delivery of Must Have requirements.


## 6. Won't Have

No specific Won't Have requirements have been identified at the current
stage.

Features that are outside the agreed current scope should be documented
and evaluated separately if they are proposed during future scope
discussions.

## 8. Prioritization Rationale

The Must Have requirements represent the minimum capabilities required
to support the core order-management process from receiving an order
through preparation and delivery.

The Should Have requirements provide additional communication, visibility,
and process-tracking benefits but are not considered essential to the
minimum operational flow.

No specific Could Have or Won't Have requirements have been identified
because these categories should be based on actual stakeholder needs and
scope decisions rather than assumptions.


## 9. Validation

The MoSCoW priorities represent the current analysis and should be
validated with relevant stakeholders.

Priority may change based on factors such as:

- Business value
- Operational impact
- Customer impact
- Implementation effort
- Project constraints
- Stakeholder expectations
- Dependencies between requirements
